# `measures.py`: the DPS numbers a player can check in-game

**Parent:** <https:../2026-11-18-000-vis-app.md> (wave 1)

## Problem Statement

Implement the design's "Measures" section as a pure module. Its consumer is
wave 2's `timeline` query, which writes each measure as one
`{"kind": "measure", "name", "value", "unit", "check"}` line, so give each
measure exactly those fields.

Each `check` is a short instruction to the player: where in-game to read or
time the value (the hero's stat panel, the sandbox training dummy, a stopwatch
from first trigger). Write checks that a player can follow.

Cover the edge cases with tests:
- a cycle with no period (`period=None`): uptime and steady DPS are undefined,
  so omit them, don't emit 0;
- `period == reload`;
- `hp` not given, and `hp` never reached within the horizon;
- zero hits.

`uptime_dps` must reproduce the in-game UI DPS for the fixtures in
`timeline_test.py` (Seven 63, Paige 64, Abrams 54). Reuse those numbers, but
don't import from a test module; copy the three `Gun(...)` literals.

**Scope (only these files):** `apps/vis/server/src/vis_server/measures.py`,
`apps/vis/server/src/vis_server/measures_test.py`

## Decisions

- **Signature `measures(cycle, horizon, hp=None) -> list[Measure]`**: it calls
  `repeat` itself, so the hits can't come from a different horizon or cycle.
  The caller calls `repeat` again for the hit lines, which is cheap.
- **`Measure` is a frozen dataclass in `measures.py`**, not in `types.py`: only
  the timeline query consumes it, and `types.py` is outside this unit's scope.
  Its fields are exactly `name, value, unit, check`; the query adds `kind`.
- **Totals count a hit when it lands by `horizon`**, not when it's triggered.
  That is what a stopwatch plus the dummy shows. `repeat` also yields hits
  triggered before the horizon that land after it; `total_damage`,
  `average_dps`, `first_land` and `time_to_kill` skip those.
- **`time_to_kill` walks the hits in land order**, because travel and cast
  delay can reorder them.
- **Undefined means omitted**: `uptime_dps` needs `period > reload`, both
  rates need a period, `first_land` needs a hit, and `time_to_kill` needs `hp`
  reached. With zero hits, the rates and totals are a real 0 and are emitted.
- **Values are unrounded**: rounding is display, so the client does it.
- **Units** are `damage/s`, `damage` and `s`.

## Open Questions

- `measures` asserts `horizon > 0` and `hp > 0`, so the timeline query must
  turn non-positive values into `BadRequest` (400), or users get a 500.
- When `hp` is given but not reached, `time_to_kill` is silently missing. The
  query could add a note ("hp not reached within {horizon} s").
- For a source with `reload == 0` (melee, casts), `uptime_dps` equals
  `steady_dps`, and its check speaks of guns first. The query could drop it
  for non-gun sources.
