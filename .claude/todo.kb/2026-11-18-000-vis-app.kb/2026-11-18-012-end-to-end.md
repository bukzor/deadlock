# `apps/vis` end to end: one command, then poke at the data in a browser

**Parent:** <https:../2026-11-18-000-vis-app.md> (wave 3, the last)

## Problem Statement

The user's acceptance bar: "I can open a browser and poke at my data". Every
component exists and passes its own checks, but nobody has used them together.
Make the whole thing work for the user, and prove it.

1. **One command.** `apps/vis/bin/serve` builds the client when needed,
   installing pnpm dependencies first, then runs `vis-server serve`, which
   serves `client/dist` and `/api` on one port. Print the URL. It is a bash
   shim: ≤50 lines, `~/.claude/must-read.kb/before/writing-bash-scripts.md`.
   The user's browser runs on Windows and the server runs in WSL2. Confirm
   Windows can reach it, for example with
   `powershell.exe -c "curl.exe -s http://localhost:8787/api"` from WSL.
   Bind to whatever address makes that work, and say why.
2. **Drive it in a real browser.** Load Skill(run) with the Skill tool; it
   covers launching the app and taking screenshots. Pick a hero, then:
   - the gun;
   - a melee attack;
   - a cast with damage over time;
   - a hero/ability pair that returns an error.

   Fix whatever is broken, wherever it is. Put the screenshots in `trash/012/`
   and name them in the Final report.
3. **Chart review.** Load Skill(dataviz) with the Skill tool (unit 006 never
   saw it), then fix what it flags. Known so far: colouring by `label` gives a
   gun 30 colours. The bars must still read as the user specified: height is
   the damage, the left edge is the trigger and the right edge is the land.
   Damage-over-time ticks now all trigger at the cast, so they overlap from
   t=0. Make that legible.
4. **Editor diagnostics.** The user's editor runs basedpyright from the repo
   root, and it reports every `starlette` import in `apps/vis/server` as
   unresolved, because it uses the root `.venv`. If a small config change
   fixes this without changing the root project's own `pyright` results, make
   it. One option is to point basedpyright at `apps/vis/server`'s own
   environment for that path. Otherwise report it.
5. **README.** `apps/vis/README.md`:
   - how to run it (the command), and how to develop it (Vite plus `serve`);
   - the protocol, by linking the design rather than copying it;
   - the `jq` examples, which are the smoke commands from unit 009.
6. **Ledger upkeep.** Drop `todo: true` from each claim whose state has now
   landed. That is the only ledger edit.
7. **Success criteria.** Check each one in the parent plan, starting from a
   clean clone (`git clone` the repo into `trash/012/clone`, then run the
   command). The local `data/` doesn't come with a clone, so point the clone at
   this checkout's data the way `deadlock.paths` allows.

**Scope:** everything under `apps/vis/`, plus the root `pyproject.toml` only
for item 4. Sibling units are all done, so no one else is editing these files.

## Decisions

- **Bind `127.0.0.1`.** This WSL2 runs `wslinfo --networking-mode` = mirrored,
  so Windows' localhost is WSL's: `curl.exe` and Windows Chrome both reached
  it. Binding `0.0.0.0` would add the LAN and the tailnet for nothing.
- **`bin/serve`** builds when a client source is newer than `dist/index.html`,
  installs when `node_modules` is older than the lockfile; `PORT` sets the port.
- **Browser:** Skill(run) and Skill(dataviz) are both "disabled for model
  invocation in skillOverrides". I drove the user's own Windows Chrome,
  headless over CDP, from WSL with `playwright-core` (scratch:
  `trash/012/driver/drive.mjs`), and reviewed the chart myself.
- **The error case:** the view can't send a bad hero/ability pair (the picker
  lists only that hero's abilities, unmodeled ones disabled), so in the
  browser it is a bad param (`horizon=abc`, 400 shown in red), and the pair
  (`hero_inferno` + `ability_icebeam`, 400) is shown by `curl.exe` from Windows.
- **Chart:** one color (a label names one hit, so it can't be a color), faint
  bars so overlapping DoT ticks darken into a staircase ending at each land,
  label in the tooltip, no legend, `nice` y, a 4 px left inset so a t=0 hit
  clears the axis. The view says when no damage lands in the horizon, shows an
  error's message without `ApiError:`, and has an empty favicon (the page's
  only 404).
- **Editor:** root `[tool.pyright] executionEnvironments` gives
  `apps/vis/server` Python 3.14 and its `.venv` site-packages. Root pyright on
  `http.py`: 30 errors without, 0 with; whole root project: 115 files, 0
  errors before and after. Needs the server's `.venv` (any `uv run` makes it).

## Open Questions

- 50-tick DoTs (Kelvin's `ability_icebeam`) saturate the staircase near the
  cast; each land rule stays distinct. A cumulative-damage line is the other
  view, not built.
- 14 abilities are listed `kind: "cast"` but draw no hits at defaults
  (duration or scaling unmodeled, e.g. `ability_afterburn`). Should `kind` be
  `null` for them?
- No `data/` gives a 500 (`FileNotFoundError` in the server log; the browser
  shows "HTTP 500: Internal Server Error"). A startup check would say more.
- `SERVE_COMMAND` expects a `verify:` from wave 3; the brief allowed only the
  `todo` edit, so it has none.
