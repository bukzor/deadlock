# `casts.py`: signature and ultimate damage as a `Cycle`

**Parent:** <https:../2026-11-18-000-vis-app.md> (wave 1)

## Problem Statement

Implement the design's "Cast" source. Given the loaded trees, a hero, an
ability key and `spirit`, return `(Cycle, notes)`, or `None` when the key isn't
one of the hero's bound signatures or ultimate, or has no `Damage`/`DPS`.
Properties are `m_mapAbilityProperties.X.m_strValue` strings; nearly all are
numeric, with known exceptions such as `"0.1m"` and `"40 30 20"`. Parse
strictly: a non-numeric value in a field you read is a `BadRequest` or a note,
your call; document which.

This model is an unverified heuristic, so the first note says so. Each
unmodeled factor present on the ability (charges, upgrades, a property that
looks damage-relevant but isn't read) gets its own note. Survey the real data
so the notes cover what actually occurs. Record the survey's counts in the
module docstring, not in a doc: the design doc belongs to the coordinator.

Tests: unit tests on synthetic trees, plus a test over the real data that every
bound signature and ultimate either yields a cycle or returns `None`, without
raising (skipped when the data is absent).

**Scope (only these files):** `apps/vis/server/src/vis_server/casts.py`,
`apps/vis/server/src/vis_server/casts_test.py`

## Decisions

- Interface: `casts.cycle(heroes, abilities, hero, ability, spirit) -> (Cycle, notes) | None`.
- Non-numeric (or missing required) read field: `BadRequest` naming the field.
  Notes would mean silently guessing a value; none occur in today's data, so a
  future one fails the real-data test, which is the signal to model it.
- DPS duration: `AbilityDuration`, else `AbilityChannelTime` (channeled ults
  such as Bebop's laser keep it there). Tick interval: `TickRate`, else
  `DPSTickInterval`, `DamageInterval`, `TickInterval`, `Interval` (all seen in
  the survey). A fallback gets a note naming the fields used. Neither found:
  DPS isn't modeled and the note lists candidate `*Duration` properties.
- A DPS tick's trigger is its interval's start, not the cast: its bar then
  spans the time the damage accrued over, and bars tile the duration instead
  of nesting from t=0. Whole ticks only; a remainder is dropped.
- Spirit: `ETechPower`, or `scale_function_tech_damage` naming no stat (36
  properties), adds `m_flStatScale x spirit`. Any other stat gets a note.
- "Looks damage-relevant": the data's own `m_bIsAbilityDamageProperty` flag.
  Matching names on `Damage` gives about 200 false hits (`IncomingDamagePercent`, ...).
- Upgrade note lists every named property bonus, via `deadlock.ability_upgrades.upgrades`.
- Zero-damage hits are dropped, so a cycle can have no hits (14 of 99 at spirit 0).
  `measures` handles zero hits.

## Open Questions

- Tick trigger convention (above) differs from guns and melee, where trigger
  is the input. Coordinator: keep it, or set ticks' trigger to the cast?
- 10 DPS abilities stay unmodeled (duration in `BurnDuration`, `DebuffDuration`,
  ...). Reading those needs per-ability knowledge; that is a later unit, not a
  heuristic to grow here.
- The upgrade note includes spirit-scale upgrades verbatim (`T2 DPS 0.6`
  beside `T2 DPS 20`), because `ability_upgrades` doesn't tell them apart.
