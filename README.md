# deadlock

Deterministic, repeatable parsing/inspection of the Deadlock (Source 2) game
binary. Three uses:

1. **Diff patches precisely** — commit the generated tables, regenerate after a
   patch, read `git diff`.
2. **Understand mechanics from data** — heroes/abilities/items as flat tables,
   not black-box play.
3. **View assets** — decompile textures/models/audio to png/glTF/wav.

Built on existing tools (no reinvention): [`vpk`] for the archive layer,
[`keyvalues3`] for KV3, and [ValveResourceFormat]'s `Source2Viewer-CLI` for
decompilation. See `docs/dev/decisions.kb/` for why.

## The tables

`data/gamedata.tsv/` holds the committed output — one row per entity, stable
sort, so a balance change is a one-line diff. Columns with the same value in
every row are kept out of `X.tsv` and listed once in `X.defaults.tsv` (absent
when there are none); `python -m deadlock.sparse dense X.tsv X.defaults.tsv`
rejoins them, and the local `data/gamedata.dense.tsv/` has the full views:

| view | what it shows |
| --- | --- |
| `levels.tsv` | player level → souls → ability-point curve |
| `heroes.tsv` | wide per-hero base stat sheet |
| `items.tsv` | shop economy: tier, resolved soul cost, slot, components |
| `abilities.tsv` | every ability bound to each live hero: signatures, guns, melee, innates, movement |
| `ability_profiles.tsv` | each weapon profile (bullet stats + derived DPS) of each live hero's bound abilities, guns included; child of `abilities.tsv` |
| `item_bonuses.tsv` | the passive stat bonuses each shop item grants |
| `ability_upgrades.tsv` | what each signature ability's three upgrades do |

`data/dlls/` holds the same kind of committed views over the game's DLLs (every
`*.dll` under `game/`), aggregated from per-DLL documents that stay local:

| view | what it shows |
| --- | --- |
| `file.tsv` | each DLL's size and sha256 |
| `load.tsv` | each DLL's load in a fresh Windows process: the modules it pulled in, the error, or why it is never loaded |
| `concommands.tsv` | every console-command declaration, per DLL in registration order, duplicates kept: name, flags, help |
| `convars.tsv` | every convar declaration, likewise: name, type, version, default, min, max, flags, help |

Every `redo` also runs the checks in `data/dlls.check/`, which fail the build if
the scan may be reading garbage: `strides` re-learns `server.dll`'s
registration-queue layout and fails if it moved; `concommands` and `convars`
fail if a known anchor or the `engine2`/`client`/`server` queue of that kind is
missing.

For reading rather than diffing, `redo data/convars.md data/concommands.md
data/dlls/load.tree.txt` renders local-only views: Markdown help pages for every
convar and console command, and `load.tsv` as a `tree(1)`-style forest of who
loads whom (a shared subtree drawn once, then marked `(*)`).

`data/deadlock-version.json` stamps which game build produced them
(`ClientVersion`, `SourceRevision`, date). To inspect a patch: update the game,
`redo`, then `git diff`.

## Setup

```sh
uv sync    # managed CPython + deps
redo       # regenerate everything from the local game install
```

`redo` provisions the latest Source2Viewer-CLI release itself, so there's no separate
bootstrap step.

Run tooling through the env wrapper: `./bin/shell pytest`, `./bin/shell pyright`.
Requires a local Deadlock install. Paths default to the stock native-Linux Steam
library (`~/.local/share/Steam/steamapps/common/Deadlock`); point
`DEADLOCK_HOME` at yours — durably, in a gitignored `localhost.env` that
`.envrc` loads:

```sh
echo 'DEADLOCK_HOME="/mnt/c/Program Files (x86)/Steam/steamapps/common/Deadlock"' > localhost.env
```

See `docs/dev/environment.kb/game-install-paths.md`.

The DLL views load the game's DLLs into Windows Python, so `redo` needs
`python.exe` on `PATH` (WSL); without it, the build fails rather than skipping them.

## CLI entry points

Each TSV view is a module reading game-data JSON on stdin; the other entry points:

```sh
python -m deadlock.manifest [vpk]                 # VPK manifest as JSONL
python -m deadlock.gamedata < file.vdata         # KV3 -> JSON
python -m deadlock.version < .../citadel/steam.inf  # build stamp as JSON
python -m deadlock.extract [--gltf] <dir> [ext…]  # extract+decompile assets
```

Assets are bulk/binary and **extracted on demand** into gitignored `data/`:

```sh
python -m deadlock.extract --gltf data/assets vmdl_c   # models -> .glb
python -m deadlock.extract data/assets vtex_c          # textures -> .png
python -m deadlock.extract data/assets vsnd_c          # audio -> .wav/.mp3
```

## About the game data

The committed TSVs are derived tables: chosen columns, joins, and computed
values (like DPS) over stats extracted from Deadlock. The underlying raw
extracts — the per-file game-data JSON and the VPK manifest — are **not
committed**; they are near-verbatim Valve data and stay local build outputs,
regenerated by `redo` from your own install.

Publishing derived stat tables follows long-standing, Valve-tolerated prior
art: SteamDB, the Deadlock community wikis, deadlock-api, and many other
datamining projects have published this class of data for years. No playable
assets (models, textures, audio) are committed.

If you're from Valve (or otherwise have a stake) and would like anything here
removed or handled differently, please open an issue — happy to discuss, and
quick to comply.

## Layout

- `src/deadlock/` — modules (≤300 lines each) with `{module}_test.py` alongside
- `docs/dev/*.kb/` — decisions, format reference, environment facts
- `data/` — generated output (only the TSV views and build stamp are tracked)
