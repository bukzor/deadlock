# `demo parser`: pick and vendor a Deadlock demo parser, prove it on a local demo

**Parent:** <../close-open-claims.md> (wave 1)

## Problem Statement

Goal: `observe` will wrap an existing Source 2 demo parser. Find the one
that parses current Deadlock `.dem` files, get it runnable in this repo,
and prove it on `game/citadel/botmatch1.dem` from the game install.
Consumers: unit 002 (counts rows by event type) and unit 004 (needs
damage events with positions and tick), so the proof must show what the
parser exposes.

Candidates to survey first (the agent in the design conversation named
these from memory; verify): `haste` (Rust, github.com/blukai/haste,
claims Deadlock support), `manta` (Go, Dota 2), `demofile-net` (C#),
`clarity` (Java). Prefer Rust or a prebuilt release. Reject anything
that does not parse the current patch's demo.

Vendoring: a redo recipe under `data/tools/` on the Source2Viewer
pattern when the parser ships a release binary; when it must be built
from source, a `.do` that runs `cargo build --release` into
`data/tools/<name>.d/` is acceptable (rustup is available). If the build
exceeds the timebox, leave the manual build in `trash/unit-001/`,
document the commands in the Final report, and say so.

Report, in `reuse-a-demo-parser.md`: parser name, version/commit, how it
is invoked, and which of these it exposes per event: tick, game time,
entity positions, combat-log damage events with attacker/victim/amount,
item purchases, ability casts, souls. Each exposed item is one line.

**Scope (only these files):** `data/tools/<parser>*` and their `.do` files;
`../claims.kb/tooling.kb/reuse-a-demo-parser.md`; this file.

## Decisions

- boon over the four named candidates: it is the only one that is
  pip-installable with a CLI and tabular datasets; haste and source2-demo
  need a Rust program per query, demofile-net and clarity need other runtimes,
  manta is Dota-only. Survey evidence: `trash/unit-001/*-README.md`.
- Vendored as a venv under `data/tools/boon.d` (not `uv add` into the
  evaluator's pyproject, which is outside this unit's scope); Python is the
  repo's `.python-version` so a later `uv add boon-deadlock` reuses uv's
  cached source-built wheel.
- Claim stays `standing: agent` (the parser choice is a judgment) but carries
  a `verify:` that reproduces the exposure facts via the CLI.

## Open Questions

- Bot demos are client-side recordings: `botmatch1.dem` has no roster
  (`boon players` is empty, `steam_id` null), `player_ticks` covers 11 heroes
  and omits hero 84 (the recording player?), and `damage` names only 7 hero
  ids, so only 1982 of 4285 hero-victim damage rows join to a position at
  their tick. Unit 003's public (server-side) demo decides whether this is
  the demo kind or the parser. Probe: `trash/unit-001/probe_join.py`.
- boon 0.19.0 carries Deadlock 6805 protobufs; the install is 6861. The
  local demos (Oct 3-7) parse; a current-patch demo is untested until 003.
- `abilities` ("important ability usage") is empty on the bot demo;
  `ability_ticks` (cooldown state changes) is the usable cast signal.

## Final report

- `redo data/tools/boon` builds (12 min cold, cargo on musl) and
  `data/tools/boon --version` prints `boon 0.19.0`; the claim's `verify:`
  runs in 12 s and prints one row per dataset.
- `reuse-a-demo-parser.md` names the parser, invocation and exposure list;
  ledger validates (`llm.kb-validate` 0 errors, `mentions` 0 findings).
- Deviations: the brief's Rust-or-binary preference yielded to a Python
  package with a Rust core; it is the only candidate exposing tables without

- Results live in `data/tools/boon.d.do`, `data/tools/boon.do` (interface:
  their header comments), and the claim file. Probes and candidate READMEs
